## 3. 面板为何这样选，哪些规则已经写入配置

选择依据已记录于 [cohort_rules.json](../config/cohort_rules.json)，不是根据旧稿“表现最好”的药物保留面板。

1. 先要求药物身份有结构支持，细胞身份可确认，有可用的基线表达和已发布响应记录。响应仅检查存在且为有限数值；不使用 AUC 大小、组间差异或任何预测结果排序。
2. 每个 GDSC DRUG_ID 只使用一个精确的 MIN_CONC/MAX_CONC 区间，按合格生物组覆盖选择；其余区间保留在审计表。每个化学身份只取一个主 GDSC ID，不将同名多个 ID 静默合并。
3. 开发至少 200 个生物组、至少 4 个组织；主外验最低 50 个生物组。本次有 58 个独立化合物满足外验至少 80 的优先目标，因此从该池选择 8 药，不需要退回最低 50 的规则。
4. 在该池内，按开发生物组数、外验生物组数、开发组织数降序，再按 GDSC ID 升序确定顺序。这是覆盖排序，不是药理类别平衡抽样，不代表临床药物总体。
5. 外验优先使用在所有 GDSC2 身份集合及其已知相关生物组之外的 CTRP 模型。本次自然外验覆盖充足，未启用“从共有细胞中再保留一部分”的备用策略。
6. 主外验只纳入 `SNP-matched-reference` 实验。`SNP-unconfirmed` 和 `SNP-not-tested` 保留在预设敏感性清单中，不擅自解释为已确认身份错误。
7. 同 compound×canonical model 的重复实验保留全部源记录；后续在规则冻结后按纳入实验的 median 响应形成一个模型级终点，不将重复实验当独立细胞。

全体 295 个 GDSC ID 的样本数见 `results/all_295_GDSC_drug_sample_counts.csv`；结构合格后的覆盖、未入选原因见 `results/all_structure_supported_drug_coverage.csv` 和 `drug_selection_decisions.csv`。选择过程可以逐步追溯，不再用“筛过后只报告高性能条件”的流程。

## 5. 身份问题已经如何处理

**细胞身份。**1,019 个表达样本中，1,018 个可按确切标识解析，`NCIH322_LUNG` 对应两个候选 ACH ID，未猜测纳入。GDSC 的 969 个模型中，963 个确切 ID 可解析；KOSC-2、MS-1、NCI-H322M、NCI-H748、SJRH30、SCC90 共 6 个有标识矛盾，作为冲突记录保留。Broad 同源组织样本信息与 Sanger patient/parent 信息联合用于已知生物组划分；未知关系仍是限制。

**药物身份。**本地 GDSC2 有 295 个 DRUG_ID、286 个主名称。64 个 ID→63 个 CTRP 单药通过当前保守结构核验；另有 21 条歧义候选关系保留。CTRP 的 545 个化合物中有 49 个明确组合药，不能切开名称或忽略比例后当单药使用。

主要例子如下：

- Docetaxel 的 GDSC 1007/1819 与 CTRP 660364 存在完整 InChIKey 立体部分不一致，暂不进入主面板；CTRP 660217 还是含 Docetaxel 的组合药，更不能混用。
- Selumetinib 1736 官方同义名中包含 AZD1480，但相应结构不符；该候选已被排除，不能只靠药名相近或同义名连接。
- Bosutinib、Serdemetan 有结构连接性冲突；部分其他药物存在盐型、多组分或未指派立体信息，均不升级为无条件合格。
- GDSC 同药多个 DRUG_ID 来自筛选追踪差异；新流程保留 ID。药物名相同不意味着可以直接平均响应。

GDSC 注释本身没有原生结构，因此证据链是“官方 ID→官方主名称→PubChem CID/完整 InChIKey→CTRP 官方 SMILES 的完整 InChIKey”。这是可追溯的结构支持，**不是对两库实验药瓶的化学鉴定**。详见 [drug_identity_audit.md](../reports/drug_identity_audit.md)。

## 7. 对新论文必须保留的边界

**旧结果须重算。**旧流程先在全部数据上做差异表达、基因对/Fisher 筛选和特征筛选，再分训练/测试集，会让测试信息进入模型开发。旧 AUC 中使用硬分类标签等问题也不能靠修正文句解决。原代码可帮助理解历史意图，但筛选结果、阈值和模型性能不能直接迁移到新稿作为验证证据。所有依赖响应的特征构造、筛选和调参须在训练折内部重新执行。

**外验性质须准确。**两组使用不同的药敏筛选来源，但都使用同版 CCLE 基线表达矩阵作为预测输入，因此这是 **cross-screen validation**，当前不构成 **cross-expression-platform validation**。CTRP 已在历史项目中使用，本次虽重新分离了身份并在建模前冻结规则，也不能写成从未接触过的前瞻盲测集。

**浓度限制须直说。**GDSC 每药固定一个浓度窗解决了库内混合问题，尚未解决 GDSC 与 CTRP 的积分区间差异。例如 Gefitinib 的 GDSC 最高浓度为 2 µM，而 CTRP 名义最高为 66 µM。主要外验可考察药物内响应排序的迁移；Spearman 不受简单单位缩放影响，但不同积分窗口可能改变细胞排序，不能声称它消除了剂量设计差异。当前不应直接比较两库绝对 AUC、跨库 RMSE 或绝对校准；统一窗口重积分应另立版本和预设方案。

**面板不等于机制或临床证据。**其中包含研究探针，不能称“8 个获批临床药物”。数据库靶点字段是名义注释，用于描述面板，不能据 REO 特征或预测表现声称验证了靶点机制、耐药因果关系或临床可用性。

## 8. 下一阶段如何衔接

1. 以正式锁文件和自动验证报告确认当前队列版本；队列、药物或身份规则如需变化，应记录版本和理由，不能根据后续外验表现更改。
2. 在开发数据上固定连续响应终点、REO 构造与并列值处理、候选规模、表达基线和简单基线，以及嵌套交叉验证和分组规则。选择基因、配对、标准化参数和模型调参都在相应训练折完成。
3. 仅在开发数据上完成计算量试跑、程序测试和必要的方法修正，冻结模型与统计方案后生成外验预测。
4. 输出每药性能、置信区间、基线差异、稳定性与失败情况，并据此决定文章结论。不预设重构后仍能维持旧稿的高分，也不把数据整理完成等同于研究已达到可投稿水平。
