# 阶段 12e：P6 v1.1 首锁前独立审查

审查状态：可首锁

日期：2026-10-15。本次独立审查仅针对 v1 首锁后、真实拟合前的元数据守卫故障及 v1.1 路径迁移。结论是**可以按既定门槛提交 v1.1 同一 Git 源码快照，再执行 `--ready`、`--lock`、`--verify-only`**；此结论不表示新锁已经生成，也不表示 64 个真实模型、第二锁或 CTRP 外验已经完成。审查中未打开 CTRP 原始曲线、响应索引或旧响应值，未运行真实最终拟合及外验。

## 核心核查结果

1. **旧失败与前序锁保持独立。** [阶段 12d 事故记录](阶段12d_P6_v1首锁后零拟合启动故障.md)记载：v1 真实启动在 `verify_freeze()` 对首锁文件求 SHA 时，旧开发守卫拒绝首个 CTRP 纯元数据 `v20._COLUMNS.txt`；输出目录、checkpoint、模型和 fit journal 均未创建，故这次启动为 0/64 任务、0/1,744 设计内 fit。独立重新计算 `config/external_validation_v1.lock.json` 的 SHA-256 为 `dcb06ab198aa52db6f264c4b33e7b6b352740b97ef15f0c73722ed33b0b46594`，与 v1.1 脚本中固定的前序锁 SHA 一致；旧 v1、v1.1 最终模型目录及 v1.1 外验目录在审查时均不存在。事故结论以旧启动异常位置、目录检查和审计记录共同支持，不把它外推为以后运行会成功。
2. **首锁输入与守卫边界一致。** [v1.1 首锁脚本](../scripts/freeze_external_validation_v1_1.py)的 `DIRECT_INPUTS` 仅把 CTRP 的 `v20._COLUMNS.txt`、`v20._README.txt`、`v20.meta.per_compound.txt` 三份明确元数据列入哈希输入（第 84–107 行）；第 110–144 行的审计守卫只对白名单放行，拒绝其余 `data_raw/ctrp` 路径、`ctrp_curve_index.csv`、其他两个 processed 响应可用性索引及旧响应。`build_lock()` 第 223–273 行还核对前序锁状态/SHA、开发锁、固定队列数与当前 Git 快照。原始曲线没有进入首锁文件清单。
3. **控制器、worker、独立审计及外验前检走同一版本。** 最终模型入口 [run_final_model_v1.py](../src/run_final_model_v1.py)第 48–51、626–663 行改用 v1.1 配置/首锁/目录及新守卫；直接 worker 和 verifier 也先执行同一首锁校验（第 332–354、645–656 行）。[独立验证](../scripts/validate_final_model_v1.py)第 36–41、386–392 行、[外验 runner](../src/run_external_validation_v1.py)第 43–50、264–275 行，以及[第二锁脚本](../scripts/freeze_external_execution_v1.py)第 21–29、99–155、174–197 行均使用 v1.1 首锁和相应新目录。外验 `--execute` 在读取 raw curve 之前先核第二锁（`run_external_validation_v1.py` 第 721–748 行），第二锁脚本要求 64 artifact、1,744 fit 及 9,480 行无响应预测清单。
4. **协议与配置版本一致。** [v1.1 协议](../docs/EXTERNAL_VALIDATION_PROTOCOL_V1_1.md)第 3、67–72 行和 [配置](../config/external_validation_v1_1.json)中的前/第二锁路径均指向 v1.1；旧 v1 路径只作为不可变前序证据。v1.1 首锁把协议、配置、事故报告、独立审查、验收、训练/评分源码及测试纳入 `EXECUTION_FILES`。报告状态门槛需唯一完整行 `审查状态：可首锁` 与 `验收状态：通过`，否则 `build_lock()` 拒绝；新锁使用排他创建，不覆盖旧锁。

## 独立运行的无响应验证

- `.venv\Scripts\python.exe -m unittest discover -s tests -p 'test_*_v1*.py' -q`：**52/52 通过**。其中 v1.1 合成测试核对旧锁 SHA、各执行入口的 v1.1 路径、三份临时元数据可读及临时 raw 曲线、processed 索引、旧响应被守卫拒绝；其他测试覆盖既有 64/1,744、网关/统计及第二锁合同。测试中出现的 fit 日志均为临时合成任务，不是真实八药拟合。
- 七个相关源码文件的 `compileall -q` 通过；`git diff --check` 无补丁空白错误。审查时 v1.1 源码、报告及测试仍是待提交工作区文件，因此尚未把 `--ready`、`--lock`、`--verify-only` 记为通过。这三步必须由提交后的同一 Git 快照执行，结果由首锁实际验收记录。

## 保留的执行与解释边界

守卫是 Python `open` 审计钩子的执行约束；首锁前检查不等于真实 64 任务一定顺利。真实运行须保留失败和资源记录，完成 64 模型及独立重载、外验 9,480 条**无响应**预测前检和 v1.1 第二锁，才能一次性读取 CTRP 响应。既往 CTRP 接触和开发集选择史仍限制外验的盲法解释；本次仅修复纯元数据哈希被错误拒绝的工程边界，不更改八药八臂、端点、配对估计量或统计族。
